# pgmpy benchmarks on GitHub CI — design

Date: 2026-11-05

## Why

The benchmarks in this repo are run by hand on one machine (results under
`results/7950x/`, dashboard on this repo's `gh-pages`). Nothing stops a pgmpy
PR from making a public method much slower, and the current suite (~435 lines
over 7 modules) covers only a small part of pgmpy's public API.

We want:

1. Every pgmpy PR checked automatically for large slowdowns, with a failing
   check when one is found.
2. A nightly run that catches slowdowns on `dev` across the whole suite,
   including the large inputs that are too slow for PRs, and keeps a
   dashboard of the history.
3. A rewritten suite that covers all of pgmpy's public classes and methods.

## Goals

- A **fast tier** that runs on every pgmpy PR, and a **slow tier** that runs
  nightly.
- The two tiers cover the **same methods**. They differ only in input size
  (small model/data for fast, large for slow). There is no "fast-only" or
  "slow-only" method, except where a benchmark has no size at all (e.g.
  `import pgmpy` time), which lives in the fast tier only.
- Coverage of every public class and method of pgmpy, per the scope rules
  below.
- A failing GitHub check when something gets meaningfully slower. That is
  the only signal: no PR comments, no issues.

## Non-goals

- The torch backend (`config.set_backend("torch")`). Left out for now.
- `pgmpy.parameterization` (marked experimental). Left out for now.
- An automated "coverage check" that flags public API without a benchmark.
  Explicitly not wanted.
- Benchmarking old pgmpy releases (the old `hashfile` of `v0.1.x` tags).
  The suite only needs to work against current `dev` and PRs on it.
- Memory benchmarks (`peakmem_`). *My call:* the check is about slowdowns,
  and memory benchmarks would roughly double run time. Time only for now.
- Multiple Python versions or OSes.

## Anti-goals

- A PR check that cries wolf. GitHub-hosted runners are noisy (10–20%
  run-to-run); a check that fails on noise will be ignored. Hence the loose
  threshold and back-to-back comparison on the same runner.
- Comparisons where base and head see different inputs. If the benchmark
  input is generated by pgmpy code that the PR changes, the comparison is
  meaningless (see "Inputs" below).
- A fast tier that blows the PR time budget and slows down contribution.

## Decided

### Where things live

- **Benchmark code** stays in this repo (`pgmpy/pgmpy-benchmarks`), branch
  `master`.
- **Both workflow files** live in the pgmpy repo (`pgmpy/pgmpy`), in
  `.github/workflows/`, next to the existing `ci.yml` and `ci-nightly.yml`.
- **Dashboard** stays on this repo's `gh-pages` branch.

### PR workflow (in pgmpy)

- Trigger: every pull request to pgmpy, like `ci.yml`. Use the same
  `concurrency` / cancel-in-progress pattern as `ci.yml`.
- Steps:
  1. Check out pgmpy (with full history, so the base commit is available).
  2. Check out this repo's `master` for the benchmark code.
  3. Run **only the fast tier** with `asv continuous`, comparing the PR's
     merge-base with `dev` against the PR head. Both commits are benchmarked
     back to back on the same runner.
- Python: **3.14** (the latest version pgmpy supports; bump as pgmpy adds
  versions). Single OS: `ubuntu-latest`.
- Threshold: fail if any benchmark is **≥ 1.5× slower** (`--factor 1.5`).
  Getting faster never fails.
- A benchmark that **errors on the PR head but works on the base** also
  fails the check. That usually means the PR broke a public API. (Builder:
  verify asv's behaviour here; if `asv continuous` doesn't already treat
  this as a failure, add a step that does.)
- The job log must show the before/after table so a contributor can see what
  regressed.
- Time budget: **one job, around 10–15 minutes in total**, including setup
  and building pgmpy twice. (The original target was 5 minutes for the asv
  run, but full coverage of ~450 public methods across two commits doesn't
  fit without cutting repeats to the point of noise. Splitting into parallel
  jobs and grouping methods were both considered and rejected in favour of a
  longer single job.) *My call on the split:* asv run ≤ ~12 minutes, whole
  job ≤ 15 minutes.
- Known, accepted consequence: because benchmarks live in a separate repo, a
  PR that intentionally changes a public API will fail this check until a
  maintainer updates the benchmarks here and re-runs the check.

### Nightly workflow (in pgmpy)

- Modelled on `ci-nightly.yml`: `schedule` cron plus `workflow_dispatch`,
  guarded by `if: github.repository == 'pgmpy/pgmpy'`. *My call:* 03:00 UTC,
  after the 02:00 test run.
- Runs the **full suite (fast + slow tiers)** on `ubuntu-latest`, Python 3.14.
- **Baseline: the `dev` commit that last night's run benchmarked.** This
  covers every PR merged that day (as one lump; a maintainer looks at the
  merged PRs to find which one caused a regression). The baseline commit is
  read from the results already pushed for the dashboard, so no extra
  bookkeeping is needed.
- Baseline and current `dev` are benchmarked back to back on the same runner
  (`asv continuous`), same 1.5× threshold, and a newly-erroring benchmark
  also counts as a failure.
- **On failure the job just fails.** No issue is opened, no comment. A
  maintainer looks at the failed run.
- **After every nightly run, results are pushed to the dashboard**, whether
  or not a regression was found. Publish first, then fail the job if needed,
  so a regression still shows up on the dashboard.
- Time budget: *my call:* aim for about 2 hours total; GitHub's hard limit
  is 6 hours per job.
- Consequence worth knowing: once a regressed commit becomes the baseline,
  the next night compares against it and passes. The failed run is the only
  signal, so a maintainer needs to notice it.

### Suite scope

Benchmark every public class and method exported via `__all__` in pgmpy's
subpackages, with these exclusions:

- **Deprecated shims** — anything that emits a deprecation warning, e.g.
  `pgmpy.estimators.HillClimbSearch`, `MaximumLikelihoodEstimator`,
  `BayesianEstimator`, `ExpectationMaximization`, `PC`, `GES`, the
  `estimators` structure scores and CI tests, `models.BayesianNetwork`,
  `models.MarkovNetwork`, `utils.get_example_model`, and deprecated methods
  on otherwise-current classes (some `CausalInference` and reader/writer
  methods). The table below is a draft; the deprecation rule wins.
  They delegate to the canonical classes that are benchmarked anyway.
  **Note:** `pgmpy.estimators` is not entirely deprecated. Non-deprecated
  classes with no canonical replacement (currently `MmhcEstimator`,
  `ExhaustiveSearch`, `MirrorDescentEstimator`, `IVEstimator`) are in scope.
- **Abstract base classes** (`Base*`, `Inference`, `StructureEstimator`, …):
  covered through their concrete subclasses.
- **Private helpers** that happen to be exported (`_return_samples`,
  `_check_*`).
- **Anything that calls an LLM**: `LLMPairwise`, `ExpertInLoop`,
  `llm_pairwise_orient`.
- **Torch/pyro-dependent code**: *my call*, following "leave torch out":
  `SEMEstimator` (requires the torch backend), `FunctionalBayesianNetwork`,
  `FunctionalCPD`.
- **Plotting**: *my call*: `to_daft`, `to_graphviz` and similar drawing
  methods.
- `pgmpy.parameterization` (non-goal above).

### Inputs

- Use seeded random generation (e.g. pgmpy's `get_random` on DAG /
  DiscreteBayesianNetwork / LinearGaussianBayesianNetwork / TabularCPD) to
  get exact sizes, and pgmpy's real example models (alarm, munin, …) where
  realism matters.
- **Inputs must be identical for base and head.** pgmpy code under test
  (e.g. `simulate`, `get_random`) can change between the two commits, which
  would silently change the inputs. *My call:* data and random models are
  generated once, with fixed seeds, independently of the pgmpy commit being
  benchmarked — either generated with plain numpy, or generated once and
  stored as fixture files (in this repo or a CI cache). The builder chooses
  which; the requirement is identical inputs.
- Example models download from the Hugging Face Hub. CI must cache the
  download directory, and loading must never be inside the timed part of a
  benchmark (use asv `setup` / `setup_cache`).

## Calls I made (for the maintainer to check)

- Both workflows run **pgmpy core dependencies only** (no `[optional]`),
  since torch, LLM and plotting code are all out of scope.
- **Results storage:** results JSON for the CI machine lives on a dedicated
  branch of this repo (not `master`), so nightly bot pushes never collide
  with humans editing benchmark code. `gh-pages` is regenerated from it with
  `asv publish`.
- **Fresh dashboard history.** The suite is rewritten, so benchmark names
  change and old graphs wouldn't line up. CI results use a new asv machine
  name (e.g. `github-ubuntu-latest`); the old `results/7950x` data stays in
  git history but is not carried over.
- **Push credential:** the nightly workflow (in pgmpy) needs write access to
  this repo. A maintainer creates a token or deploy key with push access to
  `pgmpy/pgmpy-benchmarks` and stores it as a secret in `pgmpy/pgmpy`. The
  PR workflow needs no secrets (it only reads this public repo), so it works
  for fork PRs.
- **No new commits:** if `dev` hasn't moved since last night's benchmarked
  commit, the nightly benchmarks nothing and passes. On the very first run
  (no previous results), it benchmarks `dev` only and publishes, with no
  comparison.
- **Benchmark errors on both commits:** the PR check does not fail (it isn't
  the PR's fault, e.g. a benchmark already updated on `master` for a new
  `dev` API), but the log lists it as a warning. The **nightly fails if any
  benchmark errors on current `dev`**, so broken benchmarks surface within a
  day.
- **No workflow in this repo.** Exactly two workflows, both in pgmpy, as
  agreed. Broken or over-budget benchmark changes here are caught by the next
  PR run or nightly.
- **Inherited methods** are benchmarked once, on the class that defines
  them, not again on every subclass, unless a subclass overrides the method.
- Workflow file names: `benchmarks-pr.yml` and `benchmarks-nightly.yml`.
- asv config: `environment_type: virtualenv`, `pythons: ["3.14"]`,
  `branches: ["dev"]`, `repo` pointing at the local pgmpy checkout in CI.
  The untracked local `env/` and `pgmpy/` dirs get added to `.gitignore`.
- Suite layout: one benchmark module per pgmpy subpackage (mirroring the
  table above), plus a shared module that defines the fast/slow sizes and
  builds the cached inputs.

## Left to the builder

- **How the tier is selected.** Requirement: each benchmark's logic is
  written once and instantiated at both sizes; the PR run selects the fast
  tier and the nightly selects everything with asv's `--bench` regex (or an
  equivalent asv-native mechanism). Naming scheme and class structure are
  the builder's choice.
- asv tuning (`repeat`, `number`, `rounds`, `warmup_time`, interleaving
  rounds between base and head) to stay inside the time budgets while
  keeping noise low.
- Exact model/data sizes per benchmark, within the budgets: fast tier ≤ ~12
  minutes for both commits (PR job ≤ 15 minutes); nightly ≈ 2 hours total.
  Each benchmark is its own method-level benchmark (no grouping several
  methods into one timing), apart from trivial accessors as noted below.
- Which methods of each class get benchmarked. All public methods are in
  scope; trivial accessors (`get_*` returning a stored attribute, `__repr__`,
  etc.) can be grouped or skipped where a benchmark would only measure
  Python overhead.
- How the nightly reads the previous benchmarked commit from stored results.
- Whether the PR workflow also listens on `merge_group` (other pgmpy PR
  workflows do) so it can be made a required check later without blocking
  the merge queue.
- Keeping Hugging Face network checks out of timed code (e.g. setting
  `HF_HUB_OFFLINE=1` once the cache is warm).
- Replacing the existing `benchmarks/*.py`, `results/`, `html/`, `hashfile`
  on `master` as needed.
